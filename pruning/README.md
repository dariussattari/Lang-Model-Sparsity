# pruning — structured pruning of a drone detector (Torch-Pruning)

A separate experiment track (does **not** touch `yolo/`). Question: on a CNN that
already detects drones, can **structured pruning** ([Torch-Pruning](https://github.com/VainF/Torch-Pruning))
beat **whole-model quantization** — shrinking size and latency while keeping the
task — the way the project wants task-aware compression to beat uniform compression?

## Why a different base model than `yolo/`

`yolo11n` is a COCO detector with no `drone` class, so it can't be *tailored to
drones* without fine-tuning. Instead this track starts from a CNN that detects
drones **out of the box**: [`doguilmak/Drone-Detection-YOLOv8x`](https://huggingface.co/doguilmak/Drone-Detection-YOLOv8x)
— a standard YOLOv8x fine-tuned to a single class, `drone`. On the quadcopter
video it hits **82%** at conf 0.25 (YOLO-World open-vocab managed only ~6%), and
being a plain YOLOv8 (no CLIP text tower) it prunes cleanly.

The weights (`drone_yolov8x.pt`, 137 MB) and the source video are **not** in git
(over GitHub's file limit / regenerable). Fetch the model with:

```bash
curl -L -o drone_yolov8x.pt \
  https://huggingface.co/doguilmak/Drone-Detection-YOLOv8x/resolve/main/weight/best.pt
```

## What each script does

| Script | Role |
| --- | --- |
| `prune_lib.py` | The pruning itself: swaps YOLOv8 `C2f` blocks for a chunk-free `C2f_v2` (so Torch-Pruning's DepGraph can trace the net), then `GroupNormPruner` removes channels, leaving the `Detect` head untouched. |
| `run_experiment.py` | Load base → optionally prune and/or quantize → benchmark on the video → write `runs/<name>/` in the shared schema. Used for the baseline, the naive-prune points, and quant-only. |
| `make_pseudo_dataset.py` | Builds the recovery set **from the deployment video itself**: the base model's confident boxes become pseudo-labels (task-aware, no external data). |
| `finetune.py` | Prune → **recovery fine-tune** on the pseudo-labeled video (keeping the pruned architecture) → benchmark. Supports `--quant-after` and `--from-weights`. |
| `bench.py` | Shared video benchmark; writes the model-agnostic results schema (`../analysis/RESULTS_SCHEMA.md`). |
| `summarize.py` | Collates every run into `runs/summary.{md,csv}` + `runs/comparison.png`, including **IoU vs base**. |
| `make_media.py` | Tiles the same frame from each run's annotated video into a before/after PNG. |
| `run_all.sh` | Runs the full matrix end to end. |

Reproduce everything:

```bash
python run_experiment.py --ratios 0 0.25 0.5 0.75   # base + naive-prune points
python make_pseudo_dataset.py                        # recovery set from the video
bash run_all.sh                                      # quant-only + recovery + combo
python summarize.py                                  # tables + chart
python make_media.py --frame 380                     # before/after image
```

## Results

See **`runs/summary.md`** and **`runs/comparison.png`** (regenerated by
`summarize.py`). Headline findings on the quadcopter video (MPS, conf 0.25, 34 passes):

- **Base YOLOv8x-drone (fp16):** 82% hit, 0.254 GB, ~48 ms/frame.
- **Naive structured pruning (no recovery):** detection **collapses to 0** at every
  ratio (25/50/75%). Removing channels shifts the detection head's input
  statistics, so it stops firing — this is *why* Torch-Pruning mandates a recovery
  step, and it's the CNN analogue of the "compression silently destroys a
  capability" thesis.
- **Naive int8 quant:** looks perfect on hit rate (**100%**) but is a trap —
  **IoU vs base ≈ 0.26, >200 px drift**: it emits a fixed phantom box in the corner
  of every frame and never tracks the drone. Only the IoU/localization metric
  catches this; aggregate hit rate does not.
- **Pruning + short recovery fine-tune** (on the pseudo-labeled deployment video)
  is the win: **prune 50% + recovery** keeps **IoU 0.93 / 10 px drift** vs the base
  (boxes track the drone just as well) at **~3× smaller and ~2.4× faster**;
  **prune 75% + recovery** holds the same IoU 0.93 at **~8× smaller and ~3.4×
  faster**. This is the positive result: *structured pruning with a cheap,
  task-aware recovery pass gives a better size/latency/accuracy point than
  whole-model quantization* — smaller **and** faster, with boxes that actually
  follow the drone (which int8 never does).
- **Prune + recovery + int8** reaches the smallest footprint (0.02 GB) but the int8
  step **re-breaks localization** — IoU falls back to ~0.28 (phantom corner boxes),
  same failure as int8 alone. Takeaway: on this model `quanto` int8 destroys the
  detector whether or not it's pruned; **don't stack it** — pruning + recovery is
  the compression that works here.

### Method note — measure localization, not just "did it fire"

The runs plug into the shared analysis layer, so IoU/centroid drift vs the fp16
base come for free:

```bash
python ../analysis/compare.py pruning/runs/drone_yolov8x_fp16 pruning/runs/drone_yolov8x_prune50_ft
```

Hit rate alone rewarded the broken int8 model; IoU-vs-base is what separates a real
detector from one emitting phantom boxes.

## Caveats

- Recovery fine-tunes on **pseudo-labels from the base model**, so recovered
  accuracy is bounded by the base and inherits its mistakes; it demonstrates
  *recoverability*, not a new ceiling. A human-labeled set would raise the bar.
- Weight-only quant does not speed up MPS inference (no int matmul kernels); the
  latency win here comes from **pruning** (fewer FLOPs), which is the point for edge.
- Pruned checkpoints pickle the custom `C2f_v2`; reloading a saved `runs/*/*.pt`
  needs `import prune_lib` first (done for you in `finetune.py --from-weights`).
